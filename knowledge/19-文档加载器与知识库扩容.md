# 文档加载器与知识库扩容

> 档位三的第一块：**文档加载器**。把真实网页正文抓进知识库，让片段数从 4 涨到几百条。
> 这是在「混合检索」（`18`）之后回头补的前提条件 —— 数据量太小，前面所有检索优化的收益都测不出来。

## 一、总览

| 改造 | 解决的问题 | 关键类/方法 |
|------|-----------|------------|
| 网页文档加载 | 知识库只有 4 个片段，检索优化无收益可测 | `WebPageLoader`（jsoup 抓取 + 正文清洗） |
| 正文落盘缓存 | 重复重建打目标站点、结果不可复现 | `WebPageLoader.writeCache / parseCache` |
| 来源元数据 | 不知道某段知识是从哪来的 | `Document.URL` / `Document.FILE_NAME` |
| 切分参数可配 | 300 字对整页正文偏小 | `rag.split.chunk-size / overlap` |

---

## 二、为什么要先扩知识库

混合检索做完之后，实测日志是这样的：

```
检索召回：向量 4 条 / BM25 3 条 / 融合 4 条 → rerank 取 top3
```

知识库总共只有 4 个片段，而向量召回数 `rerank.recall=20` 远大于 4，`minScore=0.2` 又几乎放行全部，
所以**向量一路就把整个知识库端上来了**。既然 `|向量 ∪ BM25| = 4` 且 `|向量| = 4`，
那 BM25 的 3 条必然是向量的子集 —— 融合结果恒等于向量结果。

结论：在这种数据量下，混合检索、RRF、甚至 rerank 的收益**都是零**，继续叠检索改造属于空转。
检索优化要能被观测，前提是「向量召回的固定条数会真正漏掉大部分片段」，也就是**知识库得先变大**。

## 三、方案：网页抓取

### 为什么不用 PDF/Word 解析器

LangChain4j 确实有 `langchain4j-document-parser-apache-pdfbox` / `-apache-poi`，
但它们的可用版本只有 **`1.4.0-beta10`**，而本项目运行时依赖的 `langchain4j-core` 是 **`1.4.0`** 正式版
（`1.4.0` 的解析器在 Maven 中央仓库不存在）。混用会让 core 被传递依赖拉到 beta 版，
或者需要手工钉版本 —— 为一个「把文本读进来」的功能引入这种版本风险不划算。

而 `jsoup` 早就写在 `pom.xml` 里（`1.17.2`，compile 作用域），代码里**一处都没用过**。
它既能抓网页、又能解析 HTML 取正文，于是这条路变成**零新增依赖**。

### 抓取策略

| 决策 | 选择 | 理由 |
|------|------|------|
| 抓取范围 | **只抓给定 URL 列表** | 行为可预测、可复现，不会失控爬到别人站点上；想扩量就往列表里加 URL |
| 并发 | 单线程 + 每次间隔 500ms | 礼貌抓取，不给目标站点压力 |
| 失败处理 | 记 warn 跳过该条 | 一个页面挂掉不该让整次入库失败（延续项目一贯的降级风格） |
| 结果 | **落盘缓存** | 见下一节 |

## 四、正文提取（启发式）

页面结构千差万别，不追求完美提取，只求「噪声少、段落结构还在」：

1. 删噪声节点：`script, style, noscript, nav, header, footer, aside, iframe, form, svg`
2. 找正文容器：依次尝试 `article` → `main` → `[role=main]` → 退回 `body`
3. **按块级元素取文本、用换行连接**（`h1~h6, p, li, pre, blockquote, dd, dt, td, th`）

第 3 步是质量关键。如果直接 `body().text()`，整页会被压成一行，
后面的 `DocumentSplitters.recursive` 就只能按字符硬切，切出来的片段语义断裂、质量很差。
按块级元素拼就能保留段落边界，切分器得以在段落级别切开。

### 踩坑记录：jsoup 的两个反直觉行为

写这块时踩了一个很隐蔽的坑，值得记下来：

```java
// 想「只保留最内层块级元素」，避免 <li><p>x</p></li> 把同一段文字算两遍
Elements blocks = root.select(BLOCK_SELECTOR);
blocks.removeIf(block -> !block.select(BLOCK_SELECTOR).isEmpty());   // ← 错
```

结果**整篇正文变成空字符串**。两个原因叠加：

1. **jsoup 的 `select` 会把元素自身也算作匹配** —— 对一个 `<p>` 调用 `p.select("p")` 返回的是 `[p]`（非空），
   所以 `!isEmpty()` 这个判断对**每一个**块级元素都成立，全被删光。
2. **jsoup 的 `Elements.removeIf` 会把元素从 DOM 里一并摘掉**（不只是从结果集合里移除）。
   验证方式：过滤后 `root.getAllElements().size()` 从 2 变成了 1 —— 正文节点真的没了。

正确写法是不碰 DOM，改用 `getAllElements()` 并排除自身来判断「有没有块级子孙」：

```java
private static boolean hasBlockDescendant(Element block) {
    for (Element element : block.getAllElements()) {
        if (element != block && element.is(BLOCK_SELECTOR)) {   // is() 判断自身是否匹配
            return true;
        }
    }
    return false;
}
```

**教训**：jsoup 的 `Elements.remove()` 系列是「操作 DOM」，不是「操作集合」。
只有明确想从文档里删节点时才用（比如删 `script`），过滤结果集千万别用。

## 五、缓存设计

一个 URL 一个文件，格式自带来源：

```
source: https://example.com/page

<清洗后的正文>
```

- **读缓存时以文件头为准**（而不是配置里的 URL），所以缓存文件改名、挪位置、调配置顺序都不丢出处
- **删掉缓存文件即重新抓取** —— 想刷新某个页面不用改代码，删文件就行
- 文件名 = URL 里非字母数字一律换下划线 + URL 哈希后缀。因此**不可能出现 `/` 或 `..`，
  天然杜绝路径穿越**；哈希后缀则避免长 URL 截断后撞名
- 缓存目录默认 `docs/web`，可以进 git：知识库属于项目资产，可复现、可审阅

## 六、来源元数据

每个片段都记录出处，用的是 **LangChain4j 约定的键**，而不是自造键名：

| 来源 | 元数据键 | 值 |
|------|---------|-----|
| 网页 | `Document.URL`（`"url"`） | 页面地址 |
| 内置文本 | `Document.FILE_NAME`（`"file_name"`） | `knowledge/java-backend.txt` |

整条链路是自动打通的，不需要额外代码：

```
Document.from(text, Metadata)          ← 加载时打上
   ↓ 切分器把 Document 的 metadata 复制到每个片段
TextSegment(text, metadata)
   ↓ MilvusEmbeddingStore 自动存成 JSON 字段（无需改 schema）
   ↓ 检索时 Mapper 自动还原
EmbeddingMatch.embedded().metadata()   ← 拿到片段就知道它出自哪
```

用约定键而不是自定义的 `source`，是为了以后接元数据过滤器、引用展示时能直接复用现成约定。

## 七、切分参数改为可配置

```yaml
rag:
  split:
    chunk-size: 500   # 原来是硬编码的 300
    overlap: 100      # 原来是硬编码的 50
```

原因：切分大小正是「文档规模变了就要调」的旋钮。300 字对短 txt 够用，
但对整页正文偏小 —— 片段承载不住一个完整概念，检索出来的东西是半截的。
这是本次唯一主动调整的检索参数，随时可以通过配置改回去。

## 九、踩坑记录：重启会重复入库（Milvus 统计接口的陷阱）

### 现象

扩容到 744 段、重建成功之后，**只要重启一次应用，日志里就会出现**：

```
集合 [level_knowledge_1789205386166] 为空，开始入库...
知识库入库完成，共 744 段
```

集合明明是刚灌满的，却被判定成「空」。而查 Milvus 的实际行数更诡异：

| 集合 | `getCollectionStatistics` 报告 | 实际入库 |
|------|-------------------------------|---------|
| 旧 `...387323`（早就写完的） | **4** ✓ | 4 |
| 新 `...386166`（刚重建的） | **0** ✗ | 744 |

### 根因

**Milvus 的 `getCollectionStatistics` 只统计已 flush 的数据**，而
`MilvusEmbeddingStore.addAll` 并不触发 flush。刚重建完的集合数据还在内存里的 growing segment 中，
统计出来的 `row_count` 就是 0，于是 `init()` 的判空逻辑认为需要入库，**把整个知识库再灌一遍**。

后果：每次重启都多一份，无上限增长。检索本身没坏（RRF 融合按文本去重会把重复片段合并掉），
但白烧 embedding 费用和存储。这是个**既有 bug**——旧的 4 段集合恰好被 flush 过所以一直没暴露，
片段数一上来就必然踩到。

### 修法：入库状态只认自己写的元文件

不去猜 Milvus 的状态，把「哪个集合、入了多少段」记进 `milvus-current-collection.txt`：

```
collection=level_knowledge_1789205780704
segments=744
```

`init()` 的判断变成：

```
元文件不存在          → 新建集合 + 入库 + 落盘元文件
元文件存在、段数一致   → 复用，跳过入库          ← 重启路径
元文件存在、段数不一致 → 复用但打 warn，提示调 /rag/rebuild（不在旧集合上重复入库）
元文件是旧格式(只有集合名) → 按「已入库」处理，只打 info
```

关键点：**元文件是入库成功之后才落盘的**，所以「元文件存在 ⟹ 入库成功过」这个推论成立，
判断是确定性的，完全不依赖 Milvus 的内部行为。顺带把 `countRows` 和 Milvus 的 v1 客户端依赖一并删掉了。

### 教训

**「集合里有多少条数据」这个问题，向量库的统计接口给的答案可能是错的。**
`row_count` 这类统计量通常基于已 flush/已 sealing 的段，写入后立刻读会读到 0。
要判断「我是否已经写过」，就自己记录状态，别去问一个语义模糊的外部接口。

## 十、已知代价：首次入库会同步阻塞启动

`RagIndexService.init()` 是 `@PostConstruct`，**首次入库是同步的**（这是刻意的：
应用起来前必须保证向量库就绪，否则第一批请求会检索失败）。

片段数上去以后这个代价就显现了。实测数字：**744 段、按每批 10 条调 75 次 DashScope，
入库耗时 30~48 秒**（`QwenEmbeddingModel` 内部 `BATCH_SIZE = 10` 自动分批）。

所以**扩容的推荐姿势是走异步重建，而不是重启**：

```
1. 把 URL 填进 rag.web.urls
2. POST /api/rag/rebuild        ← 后台线程执行，立即返回
3. GET  /api/rag/rebuild/status ← 轮询到 SUCCESS
```

入库完成后重启会直接复用集合，**实测启动 5.1 秒**，且不会重复入库（见第九节）。

## 十二、实测结果与验证要点

第一次扩容实际跑的批次：**Java 基础 14 篇 + Redis 13 篇 = 27 个页面**，全部抓取成功
（每页 2000~28700 字，是正文不是导航），得到 **744 个片段**（原 4 个），
新集合 `level_knowledge_1789205780704`，入库 30.8 秒。

检索侧的变化（扩容前 `|向量 ∪ BM25| = |向量| = 4`，BM25 恒为子集、毫无作用）：

| 查询 | 向量召回 | BM25 召回 | 最终返回 |
|------|---------|----------|---------|
| Java后端开发 | 20 | 20 | 1022 字 |
| 布隆过滤器 | 20 | **12** | 1315 字 |
| Redis 持久化 | 20 | 20 | 1357 字 |
| 缓存穿透 | 20 | 20 | 1299 字 |

**向量召回恒等于 20**（卡在 `recall` 上限）—— 744 段里它只看得到 20 条、漏掉 724 条，
混合检索这才真正有了发挥空间。这也印证了第九节开头那个判断：
**片段数太少时，检索侧的改造全是空转。**

| 验证项 | 怎么验证 |
|--------|---------|
| 清洗与缓存 | `mvn -Dtest=WebPageLoaderTest test`（不联网、不启 Spring） |
| 配置绑定 | `mvn -Dtest=WebPageLoaderPropertiesTest test`（防 `@Value` 绑不上列表那个静默坑） |
| 元文件解析 | `mvn -Dtest=RagIndexServiceMetaTest test` |
| 机制零副作用 | `rag.web.urls` 留空启动 → 日志 `网页抓取未配置（rag.web.urls 为空），跳过` |
| 文档加载 | 日志 `知识库加载完成：N 个文档 → M 个片段（chunk=500, overlap=100）` |
| 扩容生效 | 填 URL 后走 `/rag/rebuild`，M 从 4 涨到几百；`docs/web/*.txt` 抽查正文有没有混进导航/页脚 |
| **不重复入库** | 重建后**重启两次**，日志应始终是 `复用集合 [x]，跳过入库`，绝不能出现 `开始入库` |
| 检索收益 | 看 `检索召回：向量 X 条 / BM25 Y 条 / 融合 Z 条`，X 应卡在 recall 上限、且融合结果不再等于向量结果 |
| 混合检索的价值 | 把 `rag.hybrid.enabled` 改 `false` 对比同一方向，此时才真正看得出差异 |

## 十三、补数据源的实录（判断一个站点能不能当知识库）

### 数据源现状

| 批次 | 来源 | 页数 | 覆盖方向 |
|------|------|------|---------|
| 一 | javaguide.cn（java/basis、database/redis） | 27 | Java 语言基础、Redis |
| 二 | javaguide.cn（java/jvm、java/concurrent、java/collection、database/mysql、system-design/framework） | 65 | JVM、并发、集合、MySQL、Spring |
| 三 | developer.baidu.com（1 篇软件测试面试题） | 1 | 软件测试 |

**javaguide 是 Java 站，没有前端/测试栏目**，所以这两个方向必须另找数据源。

### 案例：一个「看起来有内容」的前端站，实际已下线

用户给的前端源是 `https://interview.busyhe.com/guide/`。排查过程值得记下来：

| 步骤 | 发现 |
|------|------|
| 1. 直接抓 `/guide/` | 只有 **1082 字**，内容是「前端面试题合集 内容定位…」→ **是目录页，不是正文** |
| 2. 找 sitemap | `robots.txt` 指向 `fe-interview.busyhe.com/sitemap.xml`；实际在 `interview.busyhe.com/sitemap.xml` 上有 **164 条** |
| 3. 看 sitemap 里的 URL | 全部指向 `fe-interview.busyhe.com/guide/*` |
| 4. 把主机名换成 `interview` 再抓文章页 | 全部 **404** —— 只有目录落地页存在于这台主机 |
| 5. 查 DNS | `fe-interview.busyhe.com` 是 **NXDOMAIN**（本地 DNS 和阿里公共 DNS 都说不存在）→ 子域已下线，sitemap 是旧的 |
| 6. 试其他子域 | `www`/`busyhe.com` 的 `/guide/*` 也 404；`www.busyhe.com` 首页是 **JS 渲染的 SPA**（清洗后 0 字）；`wiki` 超时 |

**结论：这个源已经不存在了，前端方向暂时无解。**

### 从这次排查得到的方法论

1. **要判断的是「文章页」，不是「首页/目录页」**。首页看起来正常，洗出来只有导航 ——
   这个坑在本项目踩过两次（javaguide 首页、busyhe 的 `/guide/`）。
   判断标准：单页清洗后 **2000 字以上**、开头是具体知识点而不是「某某合集/目录」。
2. **必须用真实抓取代码测试，不能用 curl 下结论**。这台机器上 curl 走 Windows 的 schannel，
   对 Cloudflare 站会出现 `schannel: shutting down SSL/TLS connection` 而返回 000 ——
   但 jsoup 走 Java 自己的 TLS 栈，**同一个 URL 抓得到**。差点因此误判一个可用源。
3. **sitemap 里的域名可能已经失效**。以 sitemap 为准之前先解析一下域名，
   再拿其中一条真实抓一遍。

### 案例：百度开发者中心的页脚噪声

`developer.baidu.com` 那篇能抓到（3877 字，是真文章），但**结尾混进了页脚/侧边栏**：

```
…最热文章 / 零基础调用文心大模型4.5API实操手册 / 关于作者 / 被阅读数 / 被赞数
```

原因：清洗规则只删**语义标签**（`nav/header/footer/aside`），而这个站用的是带 class 的 `<div>`，
所以漏了。切出来约 1~2 个脏片段。

**为什么这次不改清洗规则**：总量 2929 段里影响可忽略；而且盲目加
`[class*=footer]`、`[class*=recommend]` 这类子串匹配，有误删正文的风险
（比如一篇讲 CSS 侧边栏的文章，内容块的 class 可能就叫 `sidebar-demo`）。
**等接入更多非 javaguide 来源时再做，届时应换成「正文密度」这类更通用的启发式**
（挑 body 里文本量最大的块），而不是堆 class 关键词。

### 结果

| 方向 | 补数据源前 | 补之后 |
|------|-----------|--------|
| 软件测试 | 只有内置 `testing.txt`（4 段） | top-3 里出现百度那篇面试题 ✓ |
| 前端开发 | 只有内置 `frontend.txt`（4 段） | **没有变化**（源不可用） |
