# 评估集与指标（档位三收官）

> RAG 三档路线的最后一项。前面 `17`~`21` 五次改造都是靠肉眼看 top-3 来源来判断好坏，
> 这篇讲的是把那件事变成可复现的数字。
> 加/改用例不需要重新编译，改完直接 `POST /api/rag/eval` 即可，用法见 §四。

---

## 一、它解决了什么问题

### 问题一：改完不知道有没有变好

这是项目里反复出现、最消耗精力的困境。最典型的一次是 `20` 查询改写：

> 改写机制正确（LLM 扩展出的子查询质量不错），但对最终 top-3 的收益不明显。
> 且注意「有差异 ≠ 更好」：ON 让同一篇 MySQL 文章占了 top-3 里的两格，
> 而 OFF 给的是两篇不同的并发文章。

能得出这个结论，全靠**人工把两边的 top-3 来源打印出来逐条对比**。下一个改动呢？再来一遍。
改 rerank 参数、调 RRF 的 k、换切分大小……每一次都要重做这套手工比对，
而且「上一次是什么样」过几天就记不清了。

**有了评估集 + 指标，这件事变成：跑一条命令，看一张表。**
而且每次结果都落在磁盘上，可以和上一次自动做差 —— 进步的、退步的、没动的，一眼可见。

### 问题二：分不清失败是哪一类

项目反复撞同一面墙（`06`、`20` 都记着）：

> **数据覆盖度决定上限，检索技巧只能在覆盖范围内优化。**

每次「检索效果不好」，都很难快速回答：是**库里根本没有这篇文章**，还是**有但没捞到**？
分不清这两件事，就会一直在检索技巧上白费力气 —— 这就是这个项目踩过两次的坑。

评估把这件事变成**报告里的一列**：

| 原因 | 含义 | 该干什么 |
|------|------|---------|
| **不在库** | 期望的文章根本不在索引里 | **补数据** |
| **检索漏掉** | 文章在索引里但没进 topK | **调检索** |
| **调用失败** | 那一趟 API 直接报错了 | 看日志 |

判断「在不在库」用的是 `IndexManifest` 记的来源清单 ——
它本来就是本项目对「索引里有什么」的唯一权威记录（见 `24`），复用而不是去遍历 Milvus。

### 为什么现在才做

`06-下一步计划.md` 里早就把「评估集 + 指标」列为优先级 2，并写过一句：

> **评估集值得早做**：这一轮改造里反复出现「改完不知道有没有变好」的困境。
> 增量更新做完之后，这件事的性价比进一步上升 —— 现在扩知识库几乎不要成本，
> 缺的是「怎么知道检索变好了」。

`24` 增量更新完成后，加 10 个 URL 入库只要几秒；也就是说**扩数据的成本已经接近零，
瓶颈完全转移到了「怎么衡量」**。这个顺序是对的：先有便宜的扩库能力，评估才有用武之地。

## 二、架构：四件套

```
评估集（eval-set.json）               ← 查询 → 期望命中的文章，人写的「标准答案」
   ×
变体（EvalVariant）                  ← 同一批查询，不同的检索开关组合
   ↓
检索（KnowledgeService.retrieveSegments）   ← 走真实链路，绕开缓存，可选择不吃降级
   ↓
指标（RetrievalMetrics，纯函数）      ← Hit@K / MRR / Recall@K / Precision@K / Diversity@K / 耗时
   ↓
报告（report.md + report.json）       ← 变体对比表 + 未命中原因分类 + 与上次的 Δ
```

### 关键设计取舍

**① 评估层级是「文章级」而不是「片段级」**

理想的相关性标注应该标到每个片段（2929 个）—— 不现实。改成标
「这个问题该由哪篇文章回答」，人工可行，而且正好命中已知问题
（一篇文章刷屏、来源多样性失效都是在文章粒度上观察到的）。

**② 评估路径绕开缓存，且可以选择不吃降级**

生产入口 `retrieve(query)` 有两个「保护」：Caffeine 缓存 + 任何异常都 `return ""`。
这是生产该有的行为，但评估必须绕开：

- **命中缓存会让变体之间互相污染** —— 先跑「全开」把结果缓存住，
  再跑「裸向量」直接拿到全开的结果，指标全是错的
- **静默降级会让失败隐形** —— `strict=false` 时「DashScope 挂了」和「真的检索不到」
  在报告里长得一模一样，都表现为空结果

所以拆成两个入口：

| 入口 | 用途 | 缓存 | 异常 |
|------|------|------|------|
| `retrieve(query)` | **生产**，出题调用 | 读+写 | 降级成 `""` |
| `retrieveSegments(query, options, strict)` | **评估** | 不读不写 | `strict=true` 时抛出 |

**③ 参数从 `@Value` 抽成 `RetrieveOptions`，才能做变体对比**

原先 rerank / hybrid / rewrite 的开关都是启动时定死的 `@Value` 字段，
想对比「开 / 关」只能改 yml 重启应用。抽成 record 参数后，
同一批查询可以用不同参数组合连跑几遍 —— **这是变体对比能成立的前提**。

生产行为完全不变：`defaultOptions()` 把 `@Value` 组装成一份默认值，`retrieve()` 用的就是它。

**④ 单线程串行跑**

一次评估就是几百次外部 API 调用。并发会撞 DashScope 限流，
而且串行才能让「第几个变体 / 第几条用例」的进度真实可信。
用的是**独立线程池**，不复用知识库重建那个 —— 混在一起会让评估期间的
`POST /rag/rebuild` 一直排队。

## 三、指标：大白话对照表

对每条用例：取返回片段的**来源**，与期望来源比对（`rank` = 第一个命中片段的名次，从 1 开始）。

| 指标 | 大白话 | 公式 | 回答什么问题 |
|------|--------|------|-------------|
| **Hit@K** 命中率 | 十道题做对几道 | 至少命中一个期望来源的用例数 / 总用例数 | 有多少问题能找到对的文章 |
| **MRR@K** 平均倒数排名 | 正确答案排第几 | mean(1 / rank)，未命中记 0 | 排得够不够靠前（第 1 位得满分 1，第 2 位得 0.5） |
| **Recall@K** 召回率 | 该找的都找到了吗 | 被覆盖的期望来源数 / 期望来源总数 | 覆盖面够不够（多期望来源时才有意义） |
| **Precision@K** 准确率 | 找来的有多少是干货 | 命中片段数 / 返回片段总数 | 返回的内容里有多少真正有用 |
| **Diversity@K** 来源多样度 | 三个格子被几篇文章占了 | 不同来源数 / 返回片段数 | **量化 `selectDiverse`（见 `21`）的效果** |
| **AvgReturned** 平均返回数 | 平均返回了几条 | 返回片段数 / 用例数 | 防「少返回几条换多样度虚高」 |
| **EmptyRate** 空结果率 | 有几道题一条都没捞到 | 成功执行但返回空的用例占比 | 链路是不是整体失灵了 |
| **Latency p50/p95** 耗时 | 快不快、有没有长尾 | 最近秩百分位 | 每个改造值不值这个延迟 |

召回率/准确率用的是**微平均**（先各自累加再相除），不是「每条用例算一遍再平均」——
后者会让只有 1 个期望来源的用例和写了 3 个的用例权重相同，掩盖覆盖面差异。

> **所有分母为 0 的项统一返回 0，绝不产生 `NaN`。**
> 报告里出现 NaN 会一路传染，最后变成「这个指标我们不看」。

## 四、怎么用

### 1. 看/改评估集

`docs/rag-eval/eval-set.json`（30 条，进 git）。放文件系统不放 classpath，
因为它要**反复打磨**，改完立刻生效、不用重新编译。classpath 下 `rag-eval/eval-set.json` 只是兜底。

```json
{
  "id": "mysql-index-invalidation-01",
  "enabled": true,
  "query": "MySQL 索引为什么会失效？哪些写法会导致索引用不上？",
  "expectedSources": [
    "database/mysql/mysql-index-invalidation.html",
    "database/mysql/index-invalidation-caused-by-implicit-conversion.html"
  ],
  "tags": ["MySQL"],
  "note": "索引失效总篇 + 隐式转换专题"
}
```

三条写作规矩：

- **`query` 写成用户会问的自然问法**，不要写「Java后端开发」这种短标签 ——
  短标签在各种开关组合下几乎必然同结果，测不出差异
- **`expectedSources` 写路径片段就行**，会自动忽略协议/域名/`www.`/锚点/结尾斜杠。
  好处是写得短、换域名不用改评估集，内置文件（`knowledge/java-backend.txt`）也天然适用
- **`enabled: false` 可以临时屏蔽一条**而不删掉它；`id` 要唯一（有测试守着）

目前 30 条覆盖 Java基础 / JVM / 并发 / 集合 / MySQL / Redis / Spring / MyBatis / 软件测试，
其中 15 条给了 2 个期望来源（跨主题问法才有区分度）。

### 2. 跑评估

```bash
POST /api/rag/eval                                    # 跑配置默认的变体（all-on + vector-only）
POST /api/rag/eval?variants=all-on,no-rewrite         # 指定变体
POST /api/rag/eval?caseIds=mysql-btree-01             # 只跑少数几条（调评估集时省时间）
GET  /api/rag/eval/status                             # 轮询进度
GET  /api/rag/eval/report/latest                      # 拿最近一次报告
```

### 3. 看报告

`docs/rag-eval/reports/{时间戳}/` 下两个文件：

| 文件 | 给谁看 | 内容 |
|------|--------|------|
| `report.md` | 人 | 变体对比表、这组参数具体是什么、与上次的差值、未命中明细 |
| `report.json` | 程序 | 汇总指标 + 逐条明细（含实际返回了哪些来源），下次跑读它算差值 |

### 4. 变体清单

变体定义在 `EvalVariant` 枚举里（Java，类型安全）；跑哪几个由
`rag.eval.default-variants` 或请求参数决定。

| id | 含义 | 改了什么 |
|----|------|---------|
| `all-on` | 全开（**= 生产基线**） | 无 |
| `no-rewrite` | 关查询改写 | `rewrite=false` |
| `no-hybrid` | 关混合检索（只剩向量一路） | `hybrid=false` |
| `no-rerank` | 关 rerank 精排 | `rerank=false` |
| `vector-only` | 裸向量（改造前的形态） | `hybrid=false, rerank=false` |
| `no-diversity` | 全开但不限制同一来源 | `maxPerSource=0` |
| `topk-5` | 全开但取前 5 条 | `topK=5`（看召回天花板） |

代价是加变体要重新编译。**这是刻意的**：相比在 yml 里配一堆可空字段再写合并逻辑，
`UnaryOperator<RetrieveOptions>` 的组合一目了然、不会因为字段名写错而静默失效。

`all-on` 刻意用生产配置（`topK=3`），所以报告第一行就是线上真实水平。

## 五、和前面哪些知识点有关联

这张表是理解这套东西为什么长这样的关键 —— 它不是孤立的一块，而是前面所有改造的「结算方式」。

| 已有知识点 | 关联 |
|-----------|------|
| `17` RAG检索优化与降级 | 降级链保证「不能挂」，评估保证「挂了之后好不好」。两者是一对：降级是生产必须的，但它会让失败隐形；所以评估路径用 `strict=true` 反向关掉降级，专门把失败露出来 |
| `18` 混合检索 | RRF 的 `k=60`、两路各召回多少条，这些参数以前只能凭感觉调。现在 `no-hybrid` 变体直接告诉你「BM25 这一路总共值多少 Hit@K」，`topk-5` 告诉你召回上限在哪 |
| `20` 查询改写 | 那份「机制正确但对 top-3 收益不明显」的人工结论，现在变成 `no-rewrite` 变体对比表里的两行数字，**可复现、可回归**。以后再改改写策略，跑一次就知道比这次好还是差 |
| `21` 来源多样性 | `Diversity@K` 是专门为它设计的量化指标。`no-diversity` 变体关掉限制，能直接看出 `maxPerSource=1` 是赚了还是亏了 |
| `23` 检索链路与配置总览 | 里面的每个 `rag.*` 参数现在都能被评估量化。`RetrieveOptions` 的字段与那份表一一对应 |
| `24` 增量更新 | 增量让扩库成本降到几乎为零 → **「改完怎么知道变好了」成了唯一瓶颈**，所以评估的性价比随之上升。两者是配套的 |
| `19` 文档加载器 | 评估集「期望来源」用的路径片段，与网页加载器写入的 `url` 元数据、内置文件的 `file_name` 元数据直接对应 |
| `06` 的「数据覆盖度决定上限」 | **`不在库` 这一列就是那面墙的正解。** 把「该补数据还是该调检索」从凭感觉猜变成一眼可见的事实 |

一句话总结这条线：

```
14 为什么检索  →  15~16 换 Milvus  →  17~21 把检索做好（技巧）
                                          ↓
                                    22~24 把数据做大（规模）
                                          ↓
                                      25 怎么知道变好了（评估）  ← 你在这里
```

## 六、已知限制与坑

### 1. 指标好看但没意义：Hit@K 容易饱和

库里只有 96 篇、`maxPerSource=1`、`topK=3`，很多查询的正确答案就那么一两篇 ——
**Hit@3 极易饱和到 100%，变体之间零区分度**。

三个对策：评估集里放跨主题多期望来源的用例；用 `topk-5` 看天花板；
以及**给评估集持续加难样本**（这是它需要反复打磨的原因）。

### 2. 多样度可以用「少返回」作弊

返回 1 条且来源唯一 → `Diversity@K = 1.0`，比返回 3 条（0.33）还好看。

所以报告里 `AvgReturned` 永远和 `Diversity@K` 并排显示，
**只在返回数相同的变体之间比多样度**。

### 3. Δ = 0 也是一条结论

关掉 rerank 后 topK 集合完全不变 —— 这说明它只贡献延迟不贡献命中，
是**有效结论**（`20` 的查询改写就是这种情况）。报告里显式标注，别让人误以为「没生效 = 没跑」。

### 4. 评估集是回归防护网，不是质量评分

期望来源是从**现有索引**反推的，天然偏向库里已有的东西。
它回答的是「改动有没有让原本对的变错」，**不代表线上用户的真实满意度**。
报告开头就写着这句话。

### 5. 缓存污染是这套东西最致命的坑

如果评估路径误走 `RetrievalCache`，变体之间会互相命中，指标全错 ——
而且报告看起来完全正常。所以 `report.json` 里记了 `cacheDisabled: true`，
`report.md` 里也印一行「检索缓存：已绕开」。看到不是这行就说明有问题。

### 6. 评估期间索引被改 → 指标不可比

跑评估时要几分钟，这期间如果有人调 `POST /rag/rebuild`，集合会切换（见 `24`），
前后两段测的不是同一个库。所以开始和结束各记一次集合名，不一致就在报告里标
**「评估期间索引被重建过，这批指标前后不可比」**。

### 7. 成本

30 条 × 2 变体 ≈ 300 次 embedding + 60 次改写（LLM）+ 60 次 rerank，约几分钟。

- 默认只跑 `all-on` + `vector-only` 两组
- `caseIds` 只跑几条，改评估集时用
- 注意**「关 rerank」不省 embedding 钱** —— 向量召回照跑

### 8. 我没有端到端验证过

编译 + 143 个单测全绿（其中 61 个是本次新增的纯函数用例），
但**真实的评估数字没在本机跑过**（需要 Milvus + DashScope key + 应用运行）。
第一次跑出来可能命中率偏低 —— 那正是它该暴露的东西：
先看报告里「不在库」有几条，多的话说明是数据问题，不是检索问题。

## 七、代码位置

| 文件 | 职责 | 纯函数？ |
|------|------|---------|
| `model/ai/RetrieveOptions.java` | 检索参数 + wither 组合 | ✅ |
| `model/eval/*.java` | 评估集、用例、变体、指标、报告模型 | ✅ |
| `service/eval/EvalSourceMatcher.java` | 来源匹配与归一化 | ✅ |
| `service/eval/RetrievalMetrics.java` | 指标计算 + 未命中原因分类 | ✅ |
| `service/eval/EvalReportWriter.java` | 报告渲染、落盘、与上次做差 | ✅ |
| `service/eval/RagEvalSetLoader.java` | 评估集加载（文件系统 → classpath） | 部分 |
| `service/eval/RagEvalService.java` | 异步编排、进度、调检索 | ❌ Spring |
| `controller/RagEvalController.java` | 三个 HTTP 接口 | ❌ Spring |

**纯函数占了绝大多数**，这是刻意的：指标算错的后果是「看起来很专业的报告，结论全是错的」，
而且没人会怀疑一张表格。所以算法部分不依赖 Spring、不联网，可以完全离线单测。

跑单测（需要 JDK 21）：

```bash
JAVA_HOME=/e/Java/jdk-21.0.5 mvn -Dtest='EvalSourceMatcherTest,RetrievalMetricsTest,RagEvalSetTest,RetrieveOptionsTest,RagEvalPropertiesTest,EvalReportWriterTest' test
```

> `RagEvalPropertiesTest` 守的是老坑的第二次复制：`rag.eval.default-variants` 是个列表，
> 而 `@Value` **绑不上 YAML 列表**、会静默退化成空列表（见 `19` §九）。
> 所以这里用 `@ConfigurationProperties` 并配了这个绑定回归测试。
