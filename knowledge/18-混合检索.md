# 混合检索（BM25 + 向量双路召回）

> 在「Rrerank 重排序」（`17-RAG检索优化与降级`）之后做的下一块检索质量改造：**混合检索**。
> 目标是补齐向量检索的短板 —— 对专有名词、精确术语不敏感。

## 一、总览

| 改造 | 解决的问题 | 关键类/方法 |
|------|-----------|------------|
| 关键词召回 | 向量检索抓不住「布隆过滤器」这类精确术语 | `Bm25Index`（自研 BM25 + 中文 bigram 分词） |
| 双路并行召回 | 单一召回路径的盲区 | `KnowledgeService.vectorRecall / keywordRecall` |
| RRF 融合 | 两路分数不同量纲，没法直接相加 | `KnowledgeService.fuse / accumulateRrf` |
| 构建时序 | BM25 是纯内存索引，进程重启就没了 | `RagIndexService.init / doRebuild` |

---

## 二、为什么需要混合检索

### 问题：向量的盲区是「字面精确性」

向量检索是**双塔**：查询和文档各自编码成向量，再比距离。好处是能抓语义（「缓存打穿」和「缓存穿透」向量很近），
坏处是**语义被平滑**——专有名词、产品名、算法名这类信息，向量化后容易和同领域的其他词混在一起：

```
查询「布隆过滤器」
  向量检索可能返回：缓存穿透 / 缓存雪崩 / 多级缓存   ← 语义都在「缓存」这一片，但没抓住术语
  关键词检索必然返回：明确写了「布隆过滤器」的那个片段  ← 字面命中，铁证
```

反过来，能字面命中的词是**极强的相关性信号**，不该浪费。

### 方案：两路各召回一批，融合后精排

```
                         ┌── 向量召回（语义相近）──┐
查询 ──► 分词/向量化 ──┤                        ├──► RRF 融合 ──► rerank 精排 ──► top-3
                         └── BM25 召回（字面命中）─┘
```

| | 向量召回 | BM25 关键词召回 |
|---|---------|----------------|
| 匹配依据 | 语义相似度（双塔） | token 字面重合（词频统计） |
| 擅长 | 近义表达、口语化提问 | 专有名词、精确术语、代码符号 |
| 短板 | 术语被平滑、易召语义邻居 | 不会近义扩展，换个说法就召回不到 |
| 依赖 | embedding 模型 + 向量库 | 纯内存统计，无外部依赖 |

**两路互补，所以工业界主流 RAG 的召回层都是混合的。**

## 三、BM25 这一路怎么实现

### 为什么自研而不是上 Milvus 原生全文检索

Milvus 2.5 确实支持原生全文检索（sparse vector + BM25 Function），但需要：
手写 collection schema（`enable_analyzer` + `SPARSE_FLOAT_VECTOR` + BM25 `Function`）、绕过 `langchain4j-milvus` 自己建集合。
本项目知识库只有 3 个 txt、几十个片段，**改动面和风险跟收益不成比例**。
所以用一个纯内存的 BM25 索引，零新依赖、逻辑透明。

### BM25 是什么

BM25 是 TF-IDF 的改进版，解决的问题是「TF-IDF 的分数不合直觉」：

| 问题 | BM25 的对策 |
|------|------------|
| 一个词出现 100 次，就该是出现 10 次的 10 倍分吗？ | **词频饱和**：出现次数越多，边际收益越小，趋向一个上限 |
| 长文档天然会命中更多词，不公平 | **长度归一化**：文档越长，命中同样次数的得分越低 |

公式（`Bm25Index` 里落地的版本）：

```
idf(t) = ln(1 + (N - df(t) + 0.5) / (df(t) + 0.5))
score  = Σ_t idf(t) * (tf * (k1 + 1)) / (tf + k1 * (1 - b + b * dl / avgdl))

k1 = 1.2    词频饱和系数
b  = 0.75   长度归一化系数
N          = 片段总数
df(t)      = 含 token t 的片段数（越罕见 idf 越高）
tf         = token t 在本片段出现次数
dl / avgdl = 本片段长度 / 平均片段长度
```

两个工程细节：

- **idf 用 Lucene 变体**（分母 `df + 0.5` 再多加 1）：保证 idf 恒为正。
  标准 IDF 在高频词上会算出负数，导致「出现这个词反而扣分」，Lucene 的写法绕开了这个坑。
- **`dl` 的口径 = 分词后的 token 数**，不是字数、也不是词数。中文被切成 bigram，所以「缓存穿透」算 3 个 token。

### 中文分词：为什么用 bigram

BM25 依赖分词，而中文没有空格。上 jieba 会引入一个多年未更新的依赖，而 BM25 只需要「token 能重合」，
所以用 **字符 bigram**（Lucene CJK 分析器的常规做法）：

```
「缓存穿透」→ 缓存 / 存穿 / 穿透
「Redis」  → redis          （英文数字按整词、统一小写）
「缓存，穿透」→ 缓存 / 穿透   （标点作为边界，不跨标点组 bigram）
```

查询和文档用**同一个分词器**，所以「缓存穿透」查询和文档会切出同一组 token，照样能精确对上。
代价是可能产生跨词噪声（`存穿` 这种无意义组合），但 idf 会让这类高频噪声词权重自然降低。

**已知局限**：单字中文查询无法命中（索引里只有双字 token），此时 BM25 返回空、自然退回向量那一路。
实际查询是「Java后端开发」这类方向词，不受影响。

### 实现要点

- `Bm25Index` 内部持有 `volatile Snapshot`，`Snapshot` 是 record（字段全 final），**构建全新快照后整体替换**，不做增量修改
- 检索时 `Snapshot s = this.snapshot;` **只读一次引用**，避免遍历途中被重建线程换掉
- 存「全局 df 表 + 每段 tf 表 + 每段长度」，检索复杂度 O(片段数 × 查询 token 数)，几百个片段无需倒排索引
- 只返回 `score > 0` 的结果 —— 一个字面 token 都没命中就不该进候选（否则噪声污染融合结果）

## 四、RRF 融合

### 问题：两路分数不同量纲，不能直接相加

```
向量余弦相似度：[-1, 1]
BM25 得分：     无上界（几十分到几百都可能）
```

直接相加，BM25 会完全压过向量。想相加就得先归一化（min-max 归一化对 BM25 的离群值很敏感），
再加权求和（权重得调参，换个知识库还得重调）。

### 方案：RRF 只看「排名」，不看分数

```
RRF(d) = Σ_路 1 / (k + rank_路(d))          rank 从 1 开始，k = 60
```

- 一个片段在某一路排第 1，贡献 `1/61`；排第 10，贡献 `1/70`
- 在两路都排前面的片段，两份贡献叠加，自然排到最前
- **完全免疫量纲差异**：只用「谁排在前面」这个序信息，不需要归一化、不需要调权重
- `k` 起平滑作用：越大越削弱「第一名」的优势。60 是原论文默认值，这里直接沿用

**为什么这是好设计**：向量分数和 BM25 分数都不可比、不稳定，但它们各自的**排序是可信的**。
RRF 把「两个可信的排序」合成一个排序，绕开了所有标定问题。

### 去重的坑

两路返回的同一片段，**对象身份不同**——向量侧是 Milvus 反序列化出的新 `TextSegment`，BM25 侧是索引里那份。
所以去重 key 必须用 `text().trim()`，用对象 identity 是去不掉的。

融合流程：`LinkedHashMap<String, Double>` 累加分数 + `LinkedHashMap<String, TextSegment>` 存首次出现的片段对象，
再按融合分降序、截断到 `max-candidates`（默认 30，控制送进 rerank 的数据量）。

## 五、完整检索链路

```
retrieve(query)
  ├─ 0. 查缓存 RetrievalCache，命中直接返回
  ├─ 1. vectorRecall(query)   ── embed → Milvus search(maxResults=20, minScore=0.2)
  ├─ 2. keywordRecall(query)  ── Bm25Index.search(query, 20)
  ├─ 3. fuse(...)             ── RRF 融合去重，截断到 30
  ├─ 4. rerank(query, cands)  ── gte-rerank-v2 精排，取 top-3
  ├─ 5. 拼接片段原文 → 回写缓存 → 返回
  └─ 任意异常 → 返回 ""（调用方退回纯模型出题）
```

**三层的职责边界很清楚**：召回负责「别漏」（广撒网、两路互补），融合负责「合并且公平」（RRF 排掉量纲问题），
精排负责「挑最准」（交叉编码，慢但准）。

## 六、工程细节

### 坑 1：BM25 索引必须无条件构建

BM25 索引是**纯内存**的，进程一重启就没了。而 `RagIndexService.init()` 在 Milvus 集合已有数据时会**跳过入库**：

```java
if (rowCount > 0) {
    log.info("集合 [{}] 已有 {} 条向量，跳过入库", ...);   // ← 这里没有 ingest
} else {
    ingest(embeddingStore, segments);
}
bm25Index.rebuild(segments);   // ← 所以 BM25 必须在分支外面、无条件重建
```

如果把 `bm25Index.rebuild` 写进 `ingest()` 里，复用上次集合重启后 BM25 索引就是空的，
混合检索会静默退化成纯向量检索 —— 不报错，但改造白做了。

### 坑 2：重建的切换顺序

`doRebuild()` 里，**先把新的向量集合和 BM25 都建好，成功后才切 live 引用**：

```
segments = loadAndSplit()        // 切一次，向量和 BM25 共用
ingest(fresh, segments)          // 可能抛异常 → live 原封不动
bm25Index.rebuild(segments)      // 可能抛异常 → live 原封不动
currentCollectionName = newName  // ← 两次 volatile 写紧挨着
embeddingStore = fresh
retrievalCache.clearAll()
```

两次 volatile 写之间有个极小窗口，并发检索可能读到「新 BM25 + 旧向量」。
因为重建读的是同一批知识库文件、两套语料内容一致，加上融合按文本去重，
该窗口最多让某一次检索的排序略脏，**不值得为此引入额外的持有类重构** —— 这是有意识的取舍。

### 降级设计（延续项目一贯风格）

| 故障 | 行为 |
|------|------|
| embedding 调用失败 | 记 warn，本次只用 BM25 结果（以前是整体返回空） |
| BM25 召回异常 | 记 warn，本次只用向量结果 |
| `rag.hybrid.enabled=false` | 跳过 BM25，退回纯向量检索（原有行为） |
| 融合后为空 | 返回 `""`，调用方用 `NO_KNOWLEDGE_FALLBACK` |
| rerank 失败 | 退回 RRF 融合序（原有三层保护不变） |

**任一路挂了都还有另一路顶着**，比改造前「任一路异常就整体返回空」更抗故障。

## 七、配置

```yaml
rag:
  retrieve:
    top-k: 3            # 最终交给大模型的片段数
  rerank:
    enabled: true
    recall: 20          # 向量这一路召回多少候选
    model: gte-rerank-v2
    base-url: https://dashscope.aliyuncs.com/api/v1
  hybrid:
    enabled: true       # 是否开启混合检索（BM25 关键词 + 向量双路召回）
    recall: 20          # BM25 这一路召回多少条候选
    rrf-k: 60           # RRF 平滑常数，原论文默认 60
    max-candidates: 30  # 融合去重后、送进 rerank 前的候选上限
```
