# 增量更新（不全量重建）

> 档位三「数据规模」的第二项。上一项是 [19-文档加载器与知识库扩容](19-文档加载器与知识库扩容.md)。

## 一、问题

库里 2929 段，全量重建要**约 115 秒**，而这 115 秒几乎全花在 embedding 上（向量化 2929 段要调 DashScope）。
于是「加一个 URL」「改一篇文章」「修一句正文」的代价都是 2 分钟 —— 想扩知识库时，这个摩擦比技术本身更劝退。

关键在于：**跟上次比，其实只有极少数来源变了**。没变的来源，它的向量已经在 Milvus 里躺着了，
没有理由再算一遍。

## 二、方案总览

`POST /api/rag/rebuild` 现在先算一次**差分**，再决定做什么：

```
加载当前全部来源（本地缓存，不联网）
      │
      ├─ 没有来源清单 / 清单属于别的集合 / 切分参数变了 ──→ 全量重建（新建集合 + 全量灌入）
      │
      ├─ 指纹全都一致 ──→ 什么都不做，秒回「知识库无变化」
      │
      └─ 有新增/变更/删除 ──→ 增量：只对变化的来源「删旧片段 + 插新片段」
```

两种写入方式的取舍：

| | 增量（默认） | 全量（`?full=true`） |
|---|---|---|
| 集合 | 不变，原地更新 | 新建一个，成功后才切引用 |
| 代价 | 只算变化的来源（改一篇文章约 1~3 秒） | 全部重算（约 115 秒） |
| 失败影响 | **只影响出错的那个来源**，其余照常更新 | 整批失败，线上索引原封不动 |
| 用在哪 | 日常 | 换 embedding 模型、改切分参数、索引疑似脏了 |

把这张表再往下翻译一层：**增量每改动一个来源只发 2 个 Milvus 请求**（1 次删除 + 1 次插入），
其余来源一条请求都不发。省下的 115 秒不是 Milvus 的读写时间 —— 是 embedding 的调用时间。
这一层怎么落到 Milvus 上，见 §四。

为什么增量不做「新建集合 + 把未变来源的向量从旧集合搬过去」：那需要把几千条向量搬一遍、
还要用 SDK 直接查到旧集合的向量字段，代码多一大截；而原地更新只需删掉该来源的旧片段再插新的，
**代价从「搬运全部」降到「只动变化的来源」**，还顺带把「旧集合越攒越多」的问题压下去了
（现在只有全量重建会新建集合）。

## 三、来源指纹与清单

新文件 `milvus-index-manifest.txt`（和 `milvus-current-collection.txt` 并列，各管一件事）：

```
collection=level_knowledge_1789208288062
chunk=500
overlap=100
source|url|https://javaguide.cn/java/basis/proxy.html|<md5>|30
source|file_name|knowledge/java-backend.txt|<md5>|12
```

- **指纹 = 切分前正文的 MD5**。为什么不拿片段做指纹：片段是切分的产物，切分参数一改，片段就全变了，
  「内容是同一个」也会被判成「变了」。拿切分前的正文做指纹，指纹只随内容变。
- 代价是**切分参数必须单独记下来**：`chunk=500/overlap=100` 不一致时，指纹判不出差别，
  只能靠比参数拦下来 → 判定「不能增量」→ 走全量。
- `collection` 也记：清单可能属于上一个集合（比如刚做了全量重建），套用之前先比集合名。
- `chunkCount` 有两个用途：算索引总段数、算出该来源旧片段的主键范围。

字段用 `|` 分隔，不做转义 —— URL 和 classpath 路径里不会出现这个字符（URL 会编码成 `%7C`）。
字段数不是 5 的行直接跳过并告警，最坏结果是那个来源被当成新增来源重新入库（多花一次 embedding，
但不会留错数据）。

## 四、落到 Milvus 上：确定性主键，以及一次增量到底发几个请求

前面讲的是「怎么判定」，这一节讲「实际执行」—— 所有动作最终只归结为 Milvus 的**两个接口**：
`insert` 和 `delete`。没有 update、没有 upsert。

### 4.1 两个请求，一一对应

| 本项目代码 | LangChain4j | 原生 Milvus（gRPC SDK v1） | 语义 |
|---|---|---|---|
| `store.removeAll(ids)` | `MilvusEmbeddingStore.removeAll(Collection)` | `client.delete(DeleteParam.withExpr(...))` | 删掉 expr 命中的行 |
| `store.addAll(ids, embeddings, segments)` | `MilvusEmbeddingStore.addAll(...)` | `client.insert(InsertParam.withFields(...))` | 插一批行 |

`removeAll(ids)` 内部就一行（`MilvusEmbeddingStore.java:323-329`）：

```java
removeForVector(client, collectionName, format("%s in %s", idFieldName, formatValues(ids)));
```

也就是给 Milvus 发一条「按主键删」：

```
delete where expr = id in ["a1b2c3d4-...", "e5f6a7b8-...", ...]   （formatValues 会给每个 id 套双引号）
```

`addAll(ids, embeddings, segments)` 则是把 4 个字段各装成一个数组、**一次 insert 发完**
（`MilvusEmbeddingStore.java:290-305`）：`id`（主键）/ `text`（原文）/ `metadata`（JSON）/ `vector`（1536 个 float）。

所以「改一篇文章」从头到尾的请求序列是：

```
1. IndexDiff 指纹比对                → 归入 changed
2. embeddingModel.embedAll(32 段)    → DashScope HTTP，唯一慢的一步（"1~3 秒"就是它）
3. store.removeAll(ids[0..31])       → Milvus delete，1 个请求
4. store.addAll(ids[0..31], 32 向量, 32 片段) → Milvus insert，1 个请求
5. bm25Index.rebuild(全部 2929 段)    → 纯本地内存，不走网络
6. saveManifest + saveMeta + retrievalCache.clearAll()
```

对比全量：全量是**每个来源各一次 insert**（96 个来源 = 96 个请求，且每个都要先 embedding），
增量是**只有变化的来源各 2 次**（改 1 篇 = 2 个请求）。

### 4.2 为什么必须「先删后插」

**Milvus 的 insert 不做主键去重** —— 主键上没有任何唯一约束，同一个 `id` 插两次就是两行，
检索时两行都会被召回，等于同一段知识重复出现。而 Milvus 又**没有 `UPDATE` 语句**
（对照见 [17-Milvus原生语句与LangChain4j对照.md](17-Milvus原生语句与LangChain4j对照.md)），
所以「改内容」唯一的路就是把旧行换掉。

为什么不用 `upsert`：LangChain4j 这个模块根本没暴露它；而且它内部同样是「删 + 插」，
自己按来源批量做反而请求更少、时机更可控（先算向量、成功了再删，见 §五）。

### 4.3 前提机制：Milvus 的删除是「按时间戳软删」

这是「先删后插」能成立的原因，之前没写清的一层：

Milvus 的删除**不物理删数据**，而是写一条删除记录（delta log / 段级 bitset），
检索时按时间戳过滤 —— **只有「插入时间戳 < 删除时间戳」的行才会被滤掉**。由此有三条推论：

1. **顺序不能颠倒**。先 `delete` 再 `insert`，新行时间戳更晚，不会被自己刚发的那条删除干掉；
   反过来先插后删，新行会被一起删掉。
2. **删除列表里带上「还不存在的 id」是无害的** —— 匹配 0 行，而且删除不存在的 PK 不报错。
   这正是 §4.4 敢按 `max(旧段数, 新段数)` 多删几个的底气。
3. **软删的旧行还占着空间**，要等 compaction 回收（同一个 segment 里被删比例够高才触发）。
   所以「删了再插」短期是磁盘上新旧两份都在、只是旧的不可见；反复改同一个来源会攒 compaction 压力。

### 4.4 主键必须确定性生成

原来的主键是 LangChain4j 生成的随机 UUID。增量要「删掉某个来源的旧片段」，有两条路：

| 走法 | 过滤条件 | 风险 |
|------|---------|------|
| 元数据过滤 | `metadata["url"] == "..."` | 依赖 Milvus 的 JSON 字段过滤、依赖一致性级别，删除前集合必须 loaded |
| **主键删除**（选的这条） | `id in ["...", "..."]` | 最基础的能力；前提只有「集合已 loaded」 |

所以主键改成确定性生成：

```java
UUID.nameUUIDFromBytes((key + "|" + value + "#" + index).getBytes(UTF_8))
```

- `nameUUIDFromBytes` 是 MD5 派生的 v3 UUID，**跨进程稳定**，同样的来源和序号永远算出同一个 id
- 结果固定 36 字符，正好等于建集合时主键字段 `VarChar(36)` 的上限
- 于是一个来源的片段主键就是 `0 .. chunkCount-1`，**不用查 Milvus 就知道该删哪些行**

所以清单里的 `chunkCount` 不只是个统计数字 —— 它就是「该来源占哪些主键」的范围：

**删除范围取「旧段数」和「新段数」的较大值**（`max(oldCount, newCount)`）：

```java
deleteSource(store, key, Math.max(oldCount, newCount));
store.addAll(key.embeddingIds(newCount), embeddings, segments);
```

这样即使上一次跑到一半崩了（插了一半、清单没更新），下次重试时删除范围也覆盖得住残留片段，
重试基本收敛，不会越重试越多的重复行（为什么是「基本」而不是「一定」，见 §十）。

> 「主键删除没有额外前提」这句要打个折扣：Milvus 要求**删除前集合必须 loaded**，
> 否则报 `collection not loaded`。只是 `MilvusEmbeddingStore` 的构造函数末尾无条件
> `loadCollectionInMemory`，本项目又始终复用同一个 store，所以这个前提自动满足、代码里不用管。

### 4.5 想亲眼确认：数一个来源的可见行数

比翻日志直观（Attu 也能看，但 Attu 不显示被软删的行）。**按来源数行数**，直接验证「删干净了没有」：

```bash
curl -X POST "http://localhost:19530/v2/vectordb/entities/query" \
  -H "Content-Type: application/json" \
  -d '{
    "collectionName": "level_knowledge_1789208288062",
    "filter": "metadata[\"url\"] == \"https://javaguide.cn/java/basis/proxy.html\"",
    "outputFields": ["text"],
    "limit": 200
  }'
```

判读方式：**条数应该正好等于清单里该来源的 `chunkCount`**。

- 数出来多了一截 → 上次「先删后插」的删除没生效（一致性级别太低时最典型），旧的软删行还在往外冒
- 数出来少了一截 → 插入没完成，去看应用日志里那个来源的 warn

> 三个提醒：
> 1. `query` 数出来的是「**可见行数**」。`getCollectionStatistics` 的 `row_count` 是另一个口径
>    —— 它只统计**已 flush** 的数据，而本项目写入不 flush，所以刚重建完统计出来是 0，
>    不能拿它判断「入库了没有」（详见 [17-Milvus原生语句与LangChain4j对照.md](17-Milvus原生语句与LangChain4j对照.md) §3.4）。
> 2. 这里用 `metadata["url"]` 过滤只是**排查**用，读一次就完；日常删除仍然走 §4.4 的主键路径。
> 3. 这里按 url 过滤的前提是该来源是网页；内置 txt 用 `metadata["file_name"]`。

## 五、失败语义：按来源独立成功/失败

每个来源的顺序是「先 embedding（网络，最可能失败）→ 删旧片段 → 插新片段」，并且逐个来源独立处理：

- **embedding 失败** → 此时还没删任何东西 → 索引里保留旧内容，清单里那条也不更新 → 下次重建自动重试
- **某个来源失败不影响其他来源**，`status` 的 message 里会写明「N 个来源失败（保留旧内容，下次重建会重试）」

对比改造前：整批失败 = 白等 2 分钟，而且什么都没变。现在失败是「部分成功」，坏的只坏一个来源。

## 六、最危险的一步：抓取失败 ≠ 来源被删除

差分里 `removed = 清单里有 - 当前没有`。但「当前没有」有两个完全不同的原因：

1. 这个来源真的被删了（URL 从 `rag.web.urls` 里移掉、缓存文件删了）
2. **这次没抓到**（网络抖了、页面临时 503、正文清洗后为空）

如果不区分，第 2 种情况下就会把索引里的正文删掉 —— 这是整个增量更新里唯一「会造成数据损失」的地方。

所以 `WebPageLoader.load()` 的返回值从「文档列表」改成 `LoadResult(文档列表, 失败URL列表)`，
差分时把失败来源排除在 `removed` 之外，并保留它的清单条目（旧指纹、旧段数）等下次重试。
单测 `IndexDiffTest.加载失败的来源不算删除且计入失败` 就是钉这个的。

## 七、一致性级别改成 BOUNDED

`MilvusEmbeddingStore` 默认一致性是 `EVENTUALLY`，意味着**写完立刻查可能读不到**。

而 §4.3 说过：Milvus 的删除是软删、靠时间戳过滤，可见性本身就比别人慢半拍。
在 `EVENTUALLY` 下刚 `delete` 完紧接着检索，很可能旧行还没被滤掉 ——
偏偏这一轮 `insert` 已经把**同 id 的新行**写进去了，于是同一篇文章的新旧两份内容
**同时出现在召回结果里**。不只是「读到旧数据」，是「重复内容」。

改成 `ConsistencyLevelEnum.BOUNDED`（读至少能看到自己之前发出的写，允许有界延迟）：
写入方和读取方共用同一个 store 实例，所以这个保证是链路级的，不用在检索侧再做什么。

顺带修掉一个隐患：原来的全量重建也是 `EVENTUALLY`，重建完第一次检索有可能查不到新数据。

## 八、启动时的对账

启动时（`init()`，离线、只读本地缓存）会把当前知识库和清单比一次：

- 清单缺失/不属于当前集合/切分参数不符 → `warn`：下次 `POST /rag/rebuild` 会做全量重建
- 有新增/变更/删除 → `warn`：知识库与索引不一致（新增 x / 变更 y / 删除 z），调 `POST /rag/rebuild`
- 全都一致 → `info`：知识库与索引一致（N 个来源 / M 段）

这替换了原来「比 meta 文件里的段数」的做法 —— 增量更新本来就会改变段数，那个信号已经失真；
比指纹既精确，还能说清是「新增」还是「变更」。

## 九、接口与配置

```
POST /api/rag/rebuild            增量（默认）
POST /api/rag/rebuild?full=true  强制全量
GET  /api/rag/rebuild/status     轮询进度（IDLE / RUNNING / SUCCESS / FAILED）
```

`SUCCESS` 时的 message 会带上明细，例如：

```
增量完成：新增 1 / 变更 2 / 删除 0；重嵌 87 段，跳过 2842 段
知识库无变化，未做任何更新（跳过 2929 段 embedding）
全量重建完成（缺少来源清单（首次使用增量更新，或清单被删了））：重嵌 2929 段
```

```yaml
milvus:
  collection-meta-file: milvus-current-collection.txt   # 集合名 + 段数
  manifest-file: milvus-index-manifest.txt              # 每个来源的指纹 + 段数（增量依据）
```

## 十、已知代价与限制

| 限制 | 说明 |
|------|------|
| **第一次要全量** | 老部署没有清单文件，第一次 `rebuild` 会自动走全量（约 2 分钟）并写下清单，之后才快。启动日志里会有提示 |
| 某个来源更新失败时，BM25 和向量库短暂不一致 | BM25 是内存索引、每次重建都用本地正文全量重建，而失败来源的向量库里还是旧内容。会一直到下次重试成功，日志里会 warn |
| 旧集合仍在堆积 | 只有全量重建会新建集合，频率已经低很多，但还没做「切换成功后删掉旧集合」 |
| 清单被删/损坏 | 退化成全量重建（安全的一边），日志会说明原因 |
| 改切分参数必须全量 | 指纹判断不了切分边界的变化，所以清单记了 `chunk/overlap`，对不上就走全量 |
| **「重试一定收敛」有个窄口子** | 删除范围是 `max(清单旧段数, 本次新段数)`，而**崩溃那次实际插进去的数量从没被记录过**。所以「清单 30 段 → 改成 50 段、插完但保存清单前崩了 → 内容又改成 35 段」这一串下来，`max(30,35)=35` 只覆盖到 0~34，**残留 35~49 共 15 条旧内容**。需要「崩溃 + 之后内容又变短」同时成立，后果是几条陈旧片段（下次全量重建清掉）。要彻底堵住，清单里得额外记一个「曾发过的最大段数」，删除时取它和本次新段数的较大值 |
| 单次删除的 expr 长度随来源段数线性增长 | 现在每来源约 30 段（96 来源 / 2929 段），毫无压力；若出现单个几千段的超长来源，一次 `id in [...]` 会又长又慢（Milvus 对大数组 filter 的解析开销敏感，官方专门提供了 filter templating 缓解这种场景），需要改成分批删 |
| 软删的旧行要等 compaction 才回收 | 反复改同一个来源会攒 compaction 压力；磁盘上短期同时躺着新旧两份（旧的不可见） |

## 十二、验证要点

```bash
JAVA_HOME=/e/Java/jdk-21.0.5 mvn -Dtest='IndexManifestTest,IndexDiffTest,Bm25IndexTest,WebPageLoaderTest,WebPageLoaderPropertiesTest,RagIndexServiceMetaTest,QueryRewriterTest,KnowledgeServiceDiversityTest' test
```

端到端（需要 Milvus + MySQL/Redis + 启动应用）：

1. 启动应用 → 日志出现「下次 POST /rag/rebuild 会做全量重建：缺少来源清单」
2. `POST /api/rag/rebuild` → 全量（约 2 分钟），`milvus-index-manifest.txt` 生成、含 96 个 `source|` 行
3. 再 `POST /api/rag/rebuild` → **秒回**「知识库无变化，未做任何更新」
4. 改 `docs/web/` 里任一缓存文件 → rebuild → 只重嵌该来源（「重嵌 N 段，跳过 M 段」），耗时数秒
