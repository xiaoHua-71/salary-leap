# 来源多样性（避免一篇文章占满 top-k）

> 检索质量的又一块，紧接 `20-查询改写`。这篇记录的改动很小，但它暴露了一个更值得注意的问题。

## 一、问题

实测检索「Java后端开发」时，top-3 长这样：

```
top0  java-backend.txt                          （440 字）
top1  database_mysql_a_thousand_lines...        （156 字）
top2  database_mysql_a_thousand_lines...        （222 字）   ← 同一篇又占一格
```

**同一篇文章占了两格。** 为什么这是实打实的损失：

切片参数是 `chunk=500, overlap=100` —— 同一篇文章的**相邻片段自带 100 字重叠**，
所以 top1 和 top2 有很大比例是重复内容。让一篇文章占满 top-3，
等于把一整格预算花在近似重复的文字上，而不是用在别的知识上。

（这不是「多样性听起来更好」，是信息量上的直接浪费。）

## 二、方案

在 rerank 选出 top-k 的那一步，加「同一来源优先只占 N 个位置」。

```
rerank 排出完整顺序
  ↓ selectDiverse(有序候选, topK, maxPerSource)
挨个往下取：
  该来源已占满 N 个 → 先跳过，记到「跳过列表」
  否则 → 选中，该来源计数 +1
  ↓ 取够 topK 就停
  ↓ 若因为跳过而没取够，用「跳过列表」按原顺序补齐
```

**兜底那一步是刻意的**：如果不同来源本来就不够（知识库就一两篇），
宁可有重复，也不要少给知识 —— 返回 1 段和返回 3 段（含重复）相比，后者信息量更大。
所以 `max-per-source` 是**优先**而非**硬限制**。

### 实现要点

- `KnowledgeService.selectDiverse(ordered, limit, maxPerSource)` 是**纯静态方法**，
  不依赖 Spring，可以直接单测（10 个用例覆盖：跳过同源、保持顺序、兜底补齐、
  `maxPerSource<=0` 不限制、数量不足、limit 非法）
- **rerank 的四个返回路径都走它**（rereank 关闭 / 分数不匹配 / 正常 / 异常降级），
  保证「挂了」的时候行为一致，不会因为降级路径绕开多样性
- 来源取自 LangChain4j 约定元数据：网页用 `Document.URL`、内置文件用 `Document.FILE_NAME`
- **没有来源元数据的片段按 `null` 处理、不参与限制**。注意不能拿 null 当 map 的 key ——
  那样一批「来源未知」的片段会被当成同一篇互相挤掉

## 三、配置

```yaml
rag:
  retrieve:
    top-k: 3
    max-per-source: 1   # 同一篇文章优先最多占几个位置（<=0 表示不限制）
```

## 四、实测结果

| 查询 | 不限制 | `max-per-source=1` |
|------|-------|-------------------|
| Redis 持久化 | 2 个来源（persistence 占两格） | **3 个来源** ✓ |
| MySQL 索引 | 2 个来源（mysql-index 占两格） | **3 个来源** ✓ |
| Java后端开发 | 2 个来源 | 2 个来源（**没变化**） |

### 为什么 Java 那条没变化 —— 一个更值得注意的问题

不是实现错了，是**候选池本身就被一篇文章刷屏了**。

那篇「MySQL 千行笔记」正文 4 万多字，按 `chunk=500` 切出 **约 90 个片段**。
它的内容又是覆盖面很广的「学习笔记」体，所以对很多查询都能排进前列 ——
于是 rerank 之后的候选池里，大量位置被**同一篇**占据。
`selectDiverse` 把同源的都跳过之后，池子里**找不出第三个不同来源**，
兜底逻辑只好把重复的补回来。

**结论：当单篇文章的片段数量远超其他文章时，它会把召回结果「淹没」。**
这是**切片策略**层面的事，不是选择阶段能解决的。

## 五、下一步：给单篇的候选数量封顶

顺着上面的结论，真正该做的是**在候选池层面**限制单篇占比，让 rerank 拿到的是「多来源混排」，
而不是「一篇文章的 30 个片段」。两种做法：

| 做法 | 说明 | 风险 |
|------|------|------|
| 按来源分组、每组最多取 K 个进候选池 | 简单，直接 | 候选池会变小，可能丢掉真正相关的片段 |
| 按「每篇取前 K 个」再重排 | 各篇公平竞争 | 需要重新定义排序 |

或者从**切片侧**解决：超长文章用小一点 chunk，让单篇产出的片段数不失控。

**注意不要过早做这件事**：现在的 top-k=3 场景下，`selectDiverse` 已经能解决 2/3 的情况，
而且这个改动会影响送进 rerank 的候选集，可能让 rerank 失去「从同一篇里挑最相关那段」的能力。
等确实出现「目标查询被单篇淹没」的真实案例再做。
