# 检索链路与配置总览

> 检索链路经过 `17`~`21` 五次改造后，单个环节的说明分散在五篇文档里。
> 这份文档给出**当前完整的链路**和**所有可调参数**，做改动或排障时先看这里。

## 一、完整链路

### 检索时（出题触发的 `KnowledgeService.retrieve`）

```
retrieve(query)                                      ← query 是学习方向，如「Java后端开发」
  │
  ├─ 0. 查缓存（RetrievalCache，Caffeine）
  │     命中 → 直接返回，后面全跳过
  │
  ├─ 1. 查询改写（QueryRewriter）
  │     [Java后端开发, JVM内存模型与垃圾回收机制, Spring Boot自动装配原理, ...]
  │     ↑ LLM 扩展，原查询永远在第一位；失败/关闭 → 只剩原查询
  │
  ├─ 2. 每条查询各做一次双路召回
  │     ├─ 向量召回 vectorRecall：embed → Milvus search(maxResults=20, minScore=0.2)
  │     └─ BM25 召回 keywordRecall：Bm25Index.search(query, 20)   （中文 bigram 分词）
  │     某一路失败只记 warn，另一路照常工作
  │
  ├─ 3. RRF 融合（accumulateRrf）
  │     所有召回列表累加进同一张分数表：score = Σ 1/(k + rank)，k=60
  │     多路都排前面的片段分数更高（相当于多路投票）
  │     按文本去重 → 取前 max-candidates(30)
  │
  ├─ 4. rerank 精排（用**原查询**评判，不是子查询）
  │     gte-rerank-v2 给候选打分 → 排序
  │     ⚠️ 打分失败/关闭 → 退回融合顺序（此时靠 selectDiverse 选）
  │
  ├─ 5. 来源多样性选择 selectDiverse
  │     按分数顺序取 top-k(3)，同一篇文章优先只占 max-per-source(1) 个位置
  │     来源不够时用重复片段补齐（宁可重复也不少给）
  │
  └─ 6. 拼成一段文本（片段间用 \n\n---\n\n 分隔）→ 回写缓存 → 返回
        返回空串时，调用方用 NO_KNOWLEDGE_FALLBACK 兜底，退回纯模型出题

  ⚠️ 任何异常 → 返回 ""，绝不抛给上层（出题主流程不能被检索拖垮）
```

### 入库时（`RagIndexService`）

```
启动 init() / 手动 POST /rag/rebuild
  │
  ├─ 1. 加载文档 loadDocuments()
  │     ├─ 3 个内置 txt（classpath，带 file_name 元数据）
  │     └─ WebPageLoader 抓网页（带 url 元数据）
  │          · 有缓存读缓存，没缓存才联网抓
  │          · 单个 URL 失败只跳过，不打断整批
  │
  ├─ 2. 切分 loadAndSplit()：DocumentSplitters.recursive(chunk-size, overlap)
  │     元数据会复制到每个片段上
  │
  ├─ 3. 入库 ingest()：embedAll（内部按每批 10 条自动分批）→ Milvus addAll
  │
  ├─ 4. BM25 索引 bm25Index.rebuild(segments)   ← 纯内存，**每次都要建**
  │
  └─ 5. 元文件记录 collection= / segments=       ← 重启据此判断「已入库」，不重复灌
       最后清空检索缓存
```

**启动与重建的区别**：`init()` 是 `@PostConstruct`，首次入库**同步阻塞启动**（2929 段约 2 分钟）；
运行中改数据源走 `POST /rag/rebuild` 异步执行，用 `GET /rag/rebuild/status` 轮询。

## 二、所有配置项

### 检索参数

| 配置 | 默认 | 含义 |
|------|------|------|
| `rag.retrieve.top-k` | 3 | 最终交给大模型的片段数 |
| `rag.retrieve.max-per-source` | 1 | 同一篇文章**优先**最多占几个位置（`<=0` 不限制） |
| `rag.rerank.enabled` | true | 是否开启 rerank 精排 |
| `rag.rerank.recall` | 20 | **向量**这一路召回多少候选 |
| `rag.rerank.model` | gte-rerank-v2 | rerank 模型 |
| `rag.rerank.base-url` | dashscope 标准端点 | rerank 接口地址 |
| `rag.hybrid.enabled` | true | 是否开启混合检索（BM25 + 向量） |
| `rag.hybrid.recall` | 20 | **BM25** 这一路召回多少候选 |
| `rag.hybrid.rrf-k` | 60 | RRF 平滑常数（越大越削弱第一名的优势） |
| `rag.hybrid.max-candidates` | 30 | 融合去重后、送进 rerank 前的候选上限 |
| `rag.rewrite.enabled` | true | 是否开启查询改写 |
| `rag.rewrite.count` | 4 | 最多扩展出几条子查询（不含原查询） |

### 切分与入库

| 配置 | 默认 | 含义 |
|------|------|------|
| `rag.split.chunk-size` | 500 | 单个片段最大字符数 |
| `rag.split.overlap` | 100 | 相邻片段重叠字符数 |
| `rag.web.enabled` | true | 是否抓取网页入库 |
| `rag.web.urls` | 93 条 | 要抓取的页面列表；留空则跳过 |
| `rag.web.cache-dir` | docs/web | 正文缓存目录（删掉缓存文件即重新抓取） |
| `rag.web.timeout-ms` | 10000 | 单页抓取超时 |
| `rag.web.delay-ms` | 500 | 相邻两次抓取的间隔（礼貌抓取） |
| `rag.web.user-agent` | salary-leap-rag/1.0 | 抓取 UA |

### 向量库模型

| 配置 | 默认 | 含义 |
|------|------|------|
| `milvus.host` / `port` | localhost / 19530 | Milvus 地址 |
| `milvus.collection-name` | level_knowledge | 集合名前缀（实际名会拼时间戳） |
| `milvus.dimension` | 1536 | 向量维度，须与 embedding 模型一致 |
| `langchain4j.community.dashscope.chat-model.api-key` | `${DASHSCOPE_API_KEY}` | **不要写成明文**，用环境变量 |

### 代码里硬编码、暂不可配的

| 位置 | 值 | 说明 |
|------|-----|------|
| `KnowledgeService.vectorRecall` | `minScore(0.2)` | 向量相似度门槛。想调要改代码（见待办） |
| `KnowledgeService` 的 rerank 超时 | 10s | 在 `QwenScoringModel` 里 |
| `RetrievalCache` | TTL 30 分钟 / 上限 1000 条 | 可用 `rag.cache.ttl-minutes`、`rag.cache.max-size` 覆盖（yml 里未写，走默认） |
| `QwenEmbeddingModel` | 每批 10 条 | 库内部常量 `BATCH_SIZE`，不可配 |

## 三、调参速查

| 想要的效果 | 调什么 | 注意 |
|-----------|--------|------|
| 给大模型更多知识 | `rag.retrieve.top-k`↑ | 提示词变长，出题可能被无关内容干扰 |
| 召回更多候选 | `rag.rerank.recall` / `rag.hybrid.recall`↑ | 召回更多 → rerank 更慢更贵 |
| 检索更慢但更准 | 保持 `rag.rerank.enabled=true` | 关掉会退回融合顺序，质量明显下降 |
| 片段更长/更短 | `rag.split.chunk-size` | **改了必须 `/rag/rebuild`**，否则和库里数据不一致 |
| 前端/测试方向没内容 | 往 `rag.web.urls` 加 URL | 见 [06](06-下一步计划.md) 优先级 1 |
| 排查某个方向召回不好 | 看日志 `检索召回：N 条查询 → 向量 X / BM25 Y / 融合 Z` | 再配合打印片段来源定位 |

## 四、排障速查

| 现象 | 先看什么 |
|------|---------|
| 检索返回空 | 日志有没有 `检索召回`；没有就是向量/BM25 两路都空 |
| 出题内容总是那几段 | 打印 top-k 的**来源**（元数据 `url`/`file_name`），是不是某一篇在刷屏 |
| 重启后又入库一遍 | 元文件 `milvus-current-collection.txt` 的 `segments=` 是否与日志里的片段数一致 |
| 抓不到页面 | **别用 curl 测**（本机 schannel 对 Cloudflare 会误报）；看 `网页加载失败` 的 warn |
| 改了知识库但检索没变 | 是否走了 `/rag/rebuild`；检索缓存是否清掉（重建会自动清） |
| 应用起不来 | api-key 是否为空 —— `QwenEmbeddingModel` 构造时就会抛 |

## 五、日志关键字

排查时直接搜这些：

```
检索缓存命中                     ← 命中缓存，后面的链路都跳过
查询改写：Java后端开发 → 5 条      ← 改写生效
查询改写失败，退回原查询           ← 改写降级
向量召回失败，本次仅用 BM25 关键词结果
BM25 召回失败，本次仅用向量结果
检索召回：5 条查询 → 向量 100 条 / BM25 100 条 / 融合 30 条 → rerank 取 top3
Rerank 失败，退回向量检索原始顺序
知识库加载完成：96 个文档 → 2929 个片段（chunk=500, overlap=100）
网页文档加载完成：93/93 个 URL 成功
BM25 索引构建完成，共 2868 段，avgdl=164.2
复用集合 [x]，跳过入库             ← 正常重启应该是这行，不是「开始入库」
```

> 注意：`BM25 段数` 通常比片段数**少几十** —— 它按文本去重，逐字相同的片段会被合并。
