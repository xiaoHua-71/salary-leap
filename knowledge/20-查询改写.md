# 查询改写（多查询扩展）

> 档位二「检索质量」的最后一块。前面三块是 Rerank、混合检索、文档加载器。
> 这篇除了记实现，还**如实记录了一次「机制正确但没有收益」的实测结果**和原因分析 —— 这比结论本身更值钱。

## 一、总览

| 改造 | 解决的问题 | 关键类/方法 |
|------|-----------|------------|
| 多查询扩展 | 「学习方向」标签太短，召回不出知识面广度 | `QueryRewriter`、`QueryRewriteAiService` |
| N 路 RRF 融合 | 多条查询 × 两条召回路径的结果归一 | `KnowledgeService.accumulateRrf`（原样复用） |
| 降级保底 | 改写是外部依赖，挂了不能拖垮检索 | 失败路径返回「只有原查询」 |

---

## 二、为什么需要查询改写

检索的输入是一个极短的「学习方向」标签（`Java后端开发` / `前端开发` / `软件测试`）。
实测「Java后端开发」的向量召回 top-5：

```
v0 0.839  java-backend.txt
v1 0.827  java-keyword-summary.html
v2 0.827  redis-data-structures-02.html      ← Redis 文章挤进来了
v3 0.820  java-basic-questions-01.html
v4 0.820  java-basic-questions-02.html
```

两个问题：

1. **分数全挤在 0.82~0.84** —— 向量对这种短标签几乎没有区分度
2. 知识库里有 14 篇 Java 文章，只排上来 3 篇，还混进了 Redis

**根因**：用户要的是「Java 后端开发」这个**方向**，而不是某一个具体知识点。4 个字的标签
既表达不出这个方向该覆盖的知识面，向量也无从区分。
所以把标签扩展成若干条具体技术主题查询，每条各召回一批，再融合。

## 三、实现

### 链路

```
查询「Java后端开发」
  ↓ QueryRewriter：LLM 扩展成 N 条具体主题查询（原查询永远在第一位）
  [Java后端开发, JVM内存模型与垃圾回收机制, Spring Boot自动装配原理详解, ...]
  ↓ 每条查询各做一次双路召回（向量 + BM25）
  ↓ 所有召回列表累加进同一张 RRF 分数表（多路都靠前的片段分数更高）
  ↓ 按融合分取 top-30
  ↓ rerank 用**原查询**精排
  ↓ top-3 → 拼进提示词
```

### 关键设计

- **原查询永远排第一位**：`QueryRewriter.rewrite()` 先把原查询放进结果，再追加扩展项
- **失败路径 = 改造前的行为**：关闭开关 / LLM 抛异常 / 返回 null / 返回空列表，
  一律只返回「原查询单条」。所以开启改写**只会持平或更好，不会更差** —— 这是它敢默认开启的前提
- **rerank 仍用原查询**：融合出来的是候选池，最终「谁更相关」的裁判标准始终是用户真正要的方向
- **RRF 天然支持 N 路**：`accumulateRrf` 本来就是累加式，从「两路」扩到「N 条查询 × 2 条路径」
  一行不用改，只是多调用几次
- **成本**：多 1 次 LLM 调用 + 每条子查询 1 次向量化。但 `RetrievalCache` 按原查询缓存最终结果，
  所以**同一个方向只会改写一次**，重复出题不再花钱

### 复用的现成机制

`AiServices` + `@Data` POJO + `AiPrompt` 文本块（照 `LevelAiService`/`LevelResult` 抄），
`AiConfig` 注册 bean，和项目里已有的两个 AI 服务完全同构。**零新增依赖。**

## 四、实测结果：机制正确，但没有收益

LLM 扩展出来的子查询质量是好的：

| 输入 | 扩展出的子查询 |
|------|--------------|
| Java后端开发 | JVM内存模型与垃圾回收机制 / Spring Boot自动装配原理详解 / MySQL索引优化与事务隔离级别 / Redis缓存穿透雪崩解决方案 |
| 前端开发 | 浏览器渲染原理与关键路径优化 / React Fiber架构与并发更新机制 / JavaScript事件循环与异步编程模型 / Webpack构建优化与模块联邦实践 |
| 软件测试 | 黑盒测试用例设计方法 / 自动化测试框架选型与实践 / 接口测试流程与断言策略 / 性能测试指标分析与调优 |

但**对比开启/关闭改写，rerank top-3 的来源基本没变**：

```
Java后端开发   ON = OFF = [java-backend.txt, redis-3-commonly-used..., java_basis_proxy]
前端开发       ON = OFF = [frontend.txt, redis-3-commonly-used...]
软件测试       ON = OFF = [testing.txt, java_basis_unsafe...]
```

### 为什么没收益 —— 两个原因

**1. 知识库不覆盖子查询指向的主题（主因）**

LLM 扩展出的是「JVM 内存模型」「Spring Boot 自动装配」「MySQL 索引优化」这类主题 ——
但当前 KB 的 `java/basis` 是**语言基础**：

```
bigdecimal / 泛型与通配符 / 关键字 / 代理 / 反射 / 序列化 / SPI / 语法糖 / Unsafe / 值传递
```

**没有 JVM、没有并发、没有集合、没有 Spring、没有 MySQL。**
子查询问到的东西知识库里一篇都没有，召回自然捞不到新内容 —— 不是改写没生效，
是**库里没东西可捞**。

**2. rerank 用原查询评判，扩展候选赢不了**

即使扩展召回带回了新片段，最终仍由 `rerank(原查询, 候选)` 排序。
对「Java后端开发」这个短标签，分数最高的依然是标题就叫「Java 后端开发」的那个 txt，
以及语义上泛泛相关的 Redis 文章。新增的候选在「与原标签的相关性」上不占优。

### 教训

这已经是本项目第二次撞上同一面墙：**数据覆盖度决定上限，检索技巧只能在覆盖范围内优化。**

- 上一次：KB 只有 4 个片段时，混合检索/RRF/rerank 的收益全是零
- 这一次：子查询问的主题库里没有，改写再好也捞不出东西

**下次遇到「检索效果不好」，先问「库里到底有没有这东西」，再问「怎么检得更准」。**

### 补完知识库之后的复测（2026-09-12 同日）

按上面的结论先把 KB 补起来：加了 **JVM(10) + 并发(16) + 集合(12) + MySQL(16) + 框架/Spring(11) = 65 页**，
KB 从 **744 段 → 2920 段**（92 个页面 + 3 个内置 txt，共 95 个文档），重建耗时 114 秒。

复测结果——**改写终于产生差异了**：

```
Java后端开发  ON  top1/top2 = mysql-a-thousand-lines（同一篇占了两格）
              OFF top1 = concurrent-reentrantlock, top2 = concurrent-thread-pool
前端开发      ON  = OFF      （KB 无前端文档，子查询问的 React/Webpack 捞不到）
软件测试      ON  ≈ OFF      （同上，只有 top2 在一个无关片段上不同）
```

结论要看仔细，**「有差异」不等于「更好」**：

1. **Java 方向确实变了**，证明前面「库里没这东西」的诊断是对的 —— 补上 MySQL/JVM 之后，
   子查询「MySQL索引优化与事务隔离级别」真的把 MySQL 文章捞进来了
2. **但 ON 的 top-3 未必比 OFF 强**。当前一次出题只生成一道题，
   而 ON 把 3 个格子里的 2 个给了同一篇 MySQL 文章；OFF 反而给出了两篇不同的并发文章。
   对「单题」场景，广度本身不是收益
3. **冒出一个新问题：同一篇文章会占多个 top 位**。这是 rerank 只看片段相关性、
   不看来源多样性导致的，**与改写无关**，是独立可改进项

**下一步真正值得做的是「来源多样性」**：在 rerank 之后加一步，
限制同一来源最多占 N 个位置（比如 1~2），把格子让给其他文章。
这比继续在查询侧做文章更直接。

前端/测试方向仍然无解 —— **javaguide 是 Java 站，sitemap 里没有前端/测试栏目**，
要补这两个方向得换数据源。

## 七、验证要点

| 验证项 | 怎么验证 |
|--------|---------|
| 改写与降级 | `mvn -Dtest=QueryRewriterTest test`（手写 stub，不联网） |
| 改写是否生效 | 日志 `查询改写：Java后端开发 → 5 条` + `检索召回：5 条查询 → 向量 X 条 / BM25 Y 条 / 融合 30 条` |
| 降级路径 | 把 api-key 改错 → 日志 `查询改写失败，退回原查询`，检索仍正常返回 |
| 对比开关 | `rag.rewrite.enabled` 改 `false` 重启，对同一方向对比 rerank top-3 的来源 |

## 八、下一步

按性价比排序：

1. ~~加「来源多样性」限制~~ → **已完成**，见 `21-来源多样性`
2. **补前端/测试数据源**：javaguide 没有这两个栏目，得换站点。不补的话这两个方向的
   检索质量永远上不去（改写也救不了）
3. **限制单篇文章进候选池的数量**：见 `21` 第四节 —— 超长文章（如 4 万字的「MySQL 千行笔记」
   切出约 90 个片段）会把召回结果淹没，导致来源多样性限制失效
4. **改 rerank 策略**（看需求）：现在是「融合后统一用原查询精排」，可改成
   「每条子查询各自精排、各取最优、再合并」以保证**主题覆盖面**，
   代价是 rerank 调用从 1 次变 N 次。
   但**当前一次出题只生成一道题**（`LevelResult` 单个结果），并不需要跨主题广度，
   所以这条要等项目确实需要「一题覆盖多主题」时再做
5. 继续扩 KB：`java/new-features`(17)、`java/io`(4)、`database/sql`(6)、
   `high-performance/message-queue`(6)、`cs-basics/*`(67)、`distributed-system/*` 等
