# 查询改写（多查询扩展）

> 档位二「检索质量」的最后一块。前面三块是 Rerank、混合检索、文档加载器。
>
> 这篇的重点不是「怎么做」（链路本身很短），而是**它到底治什么病**，以及
> **为什么本项目里机制正确却没有收益**。后者比结论更值钱 —— 它划出了查询改写的能力边界：
> 它是**召回侧**的优化，救不了「库里没有」和「下游不用」。

## 一、总览

| 改造 | 解决的问题 | 关键类/方法 |
|------|-----------|------------|
| 多查询扩展 | 一条查询只能探一个方向，**召回有上限** | `QueryRewriter`、`QueryRewriteAiService` |
| N 路 RRF 融合 | 多条查询 × 两条召回路径的结果归一 | `KnowledgeService.accumulateRrf`（原样复用） |
| 降级保底 | 改写是外部依赖，挂了不能拖垮检索 | 失败路径返回「只有原查询」 |

---

## 二、它解决的问题：**召回上限**

### 2.1 心智模型：一次检索 = 一发探针

一条查询，就是往知识库里打出去的**一发探针**。它只能沿一个方向探一次，能捞回来的东西有个硬上限：

- **向量这一路**：查询被压成一个向量方向。方向指得准不准，取决于查询本身的信息量。
- **BM25 这一路**：只认字面重合的 token，一个字对不上就是零命中。

捞到什么，被**这发探针落在哪**钉死了。查询改写做的事就一句话：

> **把一发探针变成一组探针**，从不同角度覆盖同一个意图，再把各发探针的结果汇总。

### 2.2 它具体治两个病

**病一：词汇失配 —— 用户的词 ≠ 文档的词**

| 用户输入 | 文档里写的 |
|---|---|
| 「缓存怎么会把服务搞挂」 | 「缓存雪崩」 |

BM25 因为字面不重合，**零命中**；向量虽然能抓语义，但**查询越短，向量越糊**
（2.3 之后有实测分数佐证，短标签的 top-5 分数能挤在 0.03 的区间里）。
改写成「Redis 缓存穿透与雪崩解决方案」之后，两路都能命中。

注意：**向量检索缓解了词汇失配，但没有根治**。它只是把「必须字面相同」放宽成
「语义相近」，而这个放宽在短查询上非常有限。

**病二：信息量不足 —— 查询携带的信息少于用户意图**

「Java后端开发」这 6 个字，用户真正的意图是「把整个 Java 后端技术栈拿来考我」。
一条查询表达不出这个**面**，它只能粗略地指向库里**标题恰好带这几个字**的少数文档。
改写成 4 条具体主题，等于把「一个模糊的点」拆成「4 个可检索的坐标」。

### 2.3 它是「召回侧」技术，不是「精度侧」技术

这是理解它的关键 —— 查询改写**只做一件事：往候选池里加东西**。
它不改变「两条都命中时谁更相关」的判断，那由下游 rerank 负责。

| | 治什么 | 谁来治 |
|---|---|---|
| **召回侧**（recall） | **漏** —— 库里有，但没捞出来 | 混合检索、**查询改写** |
| **精度侧**（precision） | **错** —— 捞出来了，但排错了 | rerank、来源多样性 |

所以它要产生收益，必须**同时**满足两个前提：

1. **库里真有**那些子查询指向的内容 —— 否则探针打向空处
2. **下游愿意用**新加进来的候选 —— rerank 和截断阶段不把它们丢掉

后面第五节会看到，本项目**两条都没满足**，这才是「机制正确却没收益」的真正原因。

## 三、本项目的触发条件

检索的输入是一个极短的「学习方向」标签：`Java后端开发` / `前端开发` / `软件测试`。
实测「Java后端开发」的向量召回 top-5：

```
v0 0.839  java-backend.txt
v1 0.827  java-keyword-summary.html
v2 0.827  redis-data-structures-02.html      ← Redis 文章挤进来了
v3 0.820  java-basic-questions-01.html
v4 0.820  java-basic-questions-02.html
```

两个症状：

1. **分数全挤在 0.82~0.84** —— 向量对这种短标签几乎没有区分度
2. 知识库里有 14 篇 Java 文章，只排上来 3 篇，还混进了 Redis

**根因**：用户要的是「Java 后端开发」这个**方向**（一个知识面），
4 个字的标签既表达不出这个面该覆盖什么，向量也无从区分。
这正是 2.2 的两个病同时发作 —— **信息量不足**（表达不出「面」）+ **词汇失配**（短标签压出的向量糊成一团）。

所以解法就是把标签扩展成若干条具体技术主题，每条各召回一批，再融合。

## 四、实现

### 链路

```
查询「Java后端开发」
  ↓ QueryRewriter：LLM 扩展成 N 条具体主题查询（原查询永远在第一位）
  [Java后端开发, JVM内存模型与垃圾回收机制, Spring Boot自动装配原理详解, ...]
  ↓ 每条查询各做一次双路召回（向量 + BM25）
  ↓ 所有召回列表累加进同一张 RRF 分数表（多路都靠前的片段分数更高）
  ↓ 按融合分取 top-30
  ↓ rerank 用**原查询**精排
  ↓ top-3 → 拼进提示词
```

### 关键设计

- **原查询永远排第一位**：`QueryRewriter.rewrite()` 先把原查询放进结果，再追加扩展项
- **失败路径 = 改造前的行为**：关闭开关 / LLM 抛异常 / 返回 null / 返回空列表，
  一律只返回「原查询单条」。所以改写的**未截断候选池**只会变大，不会变小（严格的边界见 5.5）
- **rerank 仍用原查询**：融合出来的是候选池，最终「谁更相关」的裁判标准始终是用户真正要的方向
- **RRF 天然支持 N 路**：`accumulateRrf` 本来就是累加式，从「两路」扩到「N 条查询 × 2 条路径」
  一行不用改，只是多调用几次
- **成本**：多 1 次 LLM 调用 + 每条子查询 1 次向量化。但 `RetrievalCache` 按原查询缓存最终结果，
  所以**同一个方向只会改写一次**，重复出题不再花钱

### 复用的现成机制

`AiServices` + `@Data` POJO + `AiPrompt` 文本块（照 `LevelAiService`/`LevelResult` 抄），
`AiConfig` 注册 bean，和项目里已有的两个 AI 服务完全同构。**零新增依赖。**

## 五、实测：机制正确，但收益取决于「召回是不是瓶颈」

### 5.1 机制本身是好的

LLM 扩展出来的子查询质量没问题：

| 输入 | 扩展出的子查询 |
|------|--------------|
| Java后端开发 | JVM内存模型与垃圾回收机制 / Spring Boot自动装配原理详解 / MySQL索引优化与事务隔离级别 / Redis缓存穿透雪崩解决方案 |
| 前端开发 | 浏览器渲染原理与关键路径优化 / React Fiber架构与并发更新机制 / JavaScript事件循环与异步编程模型 / Webpack构建优化与模块联邦实践 |
| 软件测试 | 黑盒测试用例设计方法 / 自动化测试框架选型与实践 / 接口测试流程与断言策略 / 性能测试指标分析与调优 |

### 5.2 第一次实测：零效果

对比开启/关闭改写，rerank top-3 的来源**完全一样**：

```
Java后端开发   ON = OFF = [java-backend.txt, redis-3-commonly-used..., java_basis_proxy]
前端开发       ON = OFF = [frontend.txt, redis-3-commonly-used...]
软件测试       ON = OFF = [testing.txt, java_basis_unsafe...]
```

原因很直接：**子查询问的主题，库里一篇都没有。**

当时 KB 的 `java/basis` 是**语言基础**：
`bigdecimal / 泛型与通配符 / 关键字 / 代理 / 反射 / 序列化 / SPI / 语法糖 / Unsafe / 值传递`
—— 没有 JVM、没有并发、没有集合、没有 Spring、没有 MySQL。
子查询问「JVM 内存模型」，探针打向空处，召回自然捞不到新内容。
**不是改写没生效，是库里没东西可捞**（前提 1 不满足）。

### 5.3 补完知识库后复测：有差异，但「有差异 ≠ 更好」

按上面的结论先把 KB 补起来：加了 **JVM(10) + 并发(16) + 集合(12) + MySQL(16) + 框架/Spring(11) = 65 页**，
KB 从 **744 段 → 2920 段**（92 个页面 + 3 个内置 txt，共 95 个文档），重建耗时 114 秒。

复测结果——**改写终于产生差异了**：

```
Java后端开发  ON  top1/top2 = mysql-a-thousand-lines（同一篇占了两格）
              OFF top1 = concurrent-reentrantlock, top2 = concurrent-thread-pool
前端开发      ON  = OFF      （KB 无前端文档，子查询问的 React/Webpack 捞不到）
软件测试      ON  ≈ OFF      （同上，只有 top2 在一个无关片段上不同）
```

结论要看仔细：

1. **Java 方向确实变了**，证明 5.2 的诊断是对的 —— 补上 MySQL/JVM 之后，
   子查询「MySQL索引优化与事务隔离级别」真的把 MySQL 文章捞进来了（前提 1 满足了一半）
2. **但 ON 的 top-3 未必比 OFF 强**。当前一次出题只生成一道题，
   而 ON 把 3 个格子里的 2 个给了同一篇 MySQL 文章；OFF 反而给出了两篇不同的并发文章。
   对「单题」场景，广度本身不是收益
3. **冒出一个新问题：同一篇文章会占多个 top 位**。这是 rerank 只看片段相关性、
   不看来源多样性导致的，**与改写无关**，是独立可改进项 → 已由 `21-来源多样性` 处理

前端/测试方向仍然无解 —— **javaguide 是 Java 站，sitemap 里没有前端/测试栏目**，
要补这两个方向得换数据源（前提 1 对这两个方向**根本没满足**）。

### 5.4 为什么本项目没收益 —— 三个原因叠在一起

| # | 原因 | 对应 2.3 里的前提 |
|---|------|------------------|
| 1 | **召回根本不是瓶颈**：KB 小，且「Java后端开发」近乎查表 —— 库里就有一篇标题叫 `java-backend.txt` 的文档，单条查询已经捞得到 | 前提 2 不成立 |
| 2 | **rerank 坚持用原查询评判**：延伸召回的候选在「与原标签的相关性」上不占优，被压回去 | 前提 2 不成立 |
| 3 | **单题场景不需要广度**：一次只出一道题，覆盖多个主题没有收益 | —— |

**这就是文档读起来自相矛盾的根源**：机制治的是**召回上限**，而本项目里**召回不是瓶颈**。
所以「解决了问题」和「实测没收益」两句都能成立 —— 只是它们说的是两件事。

### 5.5 修正一句不严谨的话：「只会持平或更好」

代码注释和本文旧版都写过「开启改写**只会持平或更好，不会更差**」。这句话**只在候选池层面成立**，
到最终 top-3 这一层就不成立了。准确的边界是：

- ✅ **未截断的候选池一定是 OFF 的超集**。因为 RRF 是累加式，新查询给每个片段的贡献只增不减
  （新查询不会让任何片段的分**变小**），所以 OFF 池里的片段在 ON 池里必然还在
- ❌ **截断到 top-30 之后，就不保证包含关系了**。新候选可能把老候选挤出去。举例：
  老候选只在原查询里排第 30 名（贡献 `1/(60+30) ≈ 0.011`），
  新候选在 4 条子查询里都排第 1（贡献 `4/61 ≈ 0.066`）—— 老候选就被挤出 30 名之外了
- ❌ **rerank 之后更不保证**。rerank 只看片段与**原查询**的相关性，新挤进来的片段完全可能排在前面

这个边界恰好能解释 5.3 的复测现象：ON 未必比 OFF 好，甚至让同一篇 MySQL 文章占了两格。
**「候选池变大」不等于「最终结果变好」** —— 中间隔着截断和精排两道工序，它们各自有取舍。

### 5.6 教训

这已经是本项目第二次撞上同一面墙：**数据覆盖度决定上限，检索技巧只能在覆盖范围内优化。**

- 上一次：KB 只有 4 个片段时，混合检索/RRF/rerank 的收益全是零
- 这一次：子查询问的主题库里没有，改写再好也捞不出东西

**下次遇到「检索效果不好」，先问「库里到底有没有这东西」，再问「怎么检得更准」。**
再进一步，还要问第三句：**「检出来之后，下游有没有真的用它」** ——
本次的 rerank 用原查询评判，就是「召回侧加了、精度侧丢掉」的反面教材。

| 验证项 | 怎么验证 |

## 九、下一步

按性价比排序：

1. ~~加「来源多样性」限制~~ → **已完成**，见 `21-来源多样性`
2. **补前端/测试数据源**：javaguide 没有这两个栏目，得换站点。不补的话这两个方向的
   检索质量永远上不去（改写也救不了 —— 探针打向空处）
3. **限制单篇文章进候选池的数量**：见 `21` 第四节 —— 超长文章（如 4 万字的「MySQL 千行笔记」
   切出约 90 个片段）会把召回结果淹没，导致来源多样性限制失效
4. **改 rerank 策略**（看需求）：现在是「融合后统一用原查询精排」，可改成
   「每条子查询各自精排、各取最优、再合并」以保证**主题覆盖面**，
   代价是 rerank 调用从 1 次变 N 次。
   但**当前一次出题只生成一道题**（`LevelResult` 单个结果），并不需要跨主题广度，
   所以这条要等项目确实需要「一题覆盖多主题」时再做
5. 继续扩 KB：`java/new-features`(17)、`java/io`(4)、`database/sql`(6)、
   `high-performance/message-queue`(6)、`cs-basics/*`(67)、`distributed-system/*` 等
